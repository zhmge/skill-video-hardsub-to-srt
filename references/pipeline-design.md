# Pipeline 设计与实测依据

**何时读**：准备改动 `scripts/hardsub_extract.py`；怀疑有漏句或时间轴错乱；需要向用户解释为什么这么慢、为什么某些「优化」不能用。

## 四阶段流水线

```
阶段1  逐帧解码 + 逐帧文本检测(det)
       ffmpeg 管道只输出 crop 后的 ROI 行 → 每帧跑 det → 记录 has_sub[] 和 geoms[]
阶段2  投票平滑 + 切段
       N 帧滑动窗口投票去抖动 → 按 min_dur 过滤 → 得到 segments[]
阶段3  段内 OCR（几何变化触发 + 兜底）
       段内并集包围盒显著变化即触发一次 OCR；距上次 OCR 超过 0.75s 也强制一次
阶段4  归并 + 写 SRT
       按时间给每个 OCR 结果分配区间 → rapidfuzz 合并相邻同文本 → 时长/重叠清理 → SRT
```

中间数据结构：

- `has_sub[]`：每帧 bool，det 是否检出文字；
- `geoms[]`：每帧所有检测框的并集包围盒 `(x0,y0,x1,y1)`，无文字时为 `None`；
- `segments[]`：`(start_frame, end_frame)` 列表，即投票平滑后的连续有字幕区间；
- `ocr_jobs[]`：需要跑完整 OCR 的帧号集合；
- `entries[]` → `merged[]`：带 `start/end/text` 的字幕条目。

## 六条教训的展开

### 教训 1：帧差预筛被证伪（两次）

**动机**：60fps 逐帧 det 很贵，本能会想「先用帧差找出画面变化，只在变化时检测」。

**第一次尝试：固定阈值帧差。** 抽样统计发现，动画/实拍背景的帧间平均绝对差（mean absdiff）常年落在 **15~28**，而字幕切换（一句换另一句）带来的差异只有 **2~17**——两者区间重叠且噪声更高。阈值设 12 会导致每个字幕段之间出现约 30s 的空洞（漏句）；阈值设 2 则几乎每帧都触发（等于没筛）。

**第二次尝试：固定间隔抽帧。** 也不行——它对「字幕什么时候出现」是盲的，无法保证覆盖，会随机漏句。用户当初也正是担心这一点（「如果只抽取 40 帧，可以保证所有字幕都被截取吗？」）。

**结论**：**纯逐帧 det**。det 本身很便宜（24ms/帧，见教训 5），昂贵的是想省它的那些聪明办法。

### 教训 2：ffmpeg 管道的字节流错位

**现象**：处理一个 716s、60fps 的视频，只得到 7201 个「帧」——换算过去只有约 24 秒。

**原因**：管道输出的是**整帧**（`1080 × 1920 × 3` 字节），但读取端按 ROI 的**行数**（216 行）去 `read(frame_size)`。于是每「帧」拿到的是画面顶部 216 行（1080p 下正好是顶部约 20%），把整个时间轴压缩成了原片的前 1/30。

**定位方法**：把第一个「帧」dump 成 PNG 一看——显示的是顶部的水印条，不是字幕区。

**修复**：给 ffmpeg 加 `-vf crop=W:H:0:y0`，让管道**只输出 ROI 行**：

```
crop={width}:{roi_h}:0:{roi_y0}
```

附带收益：管道带宽降到约 1/5（1080p 下 ROI 只占 18%~20% 高度），解码后的数据搬运也更省。

**不要改回「读整帧再切」**，那会直接破坏时间轴。

### 教训 3：只 OCR 段中间帧会丢句

**现象**：把每个 segment 只 OCR 一次（取段中间帧），相邻的无缝字幕会互相顶掉。典型例子：一段里 det 连续为真（因为两句之间没有空帧），中间帧只识别到「可以见证自己的装备栏」，而紧邻的「让玩家可以迅速升到10级」整句丢失。

**原因**：切段依据是「有/无字幕」，而不是「是哪句字幕」。两句字幕中间没有空白间隔时，会被并入同一段。

**修复**：段内做**几何变化触发**——

- 段起点先 OCR 一次；
- 之后逐帧比较 `geoms[f]` 与上次触发时的包围盒，若任一坐标差超过容差（约 **6px**），说明字幕换了（或从单行变成了双行），就再 OCR 一次；
- 兜底：距上次 OCR 超过 **0.75s** 强制 OCR 一次，应对「文字变了但包围盒几乎没变」。

**效果**：2 分钟样本从 **9 条 → 70 条**。

### 教训 4：PaddleX 模型源

`PP-OCRv5_mobile_det_safetensors` 在 aistudio / modelscope 源上返回 404（modelscope 甚至返回 `<Response [404]>`），HF 源间歇性 502 但可重试成功。故必须：

```
PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True
PADDLE_PDX_MODEL_SOURCE=huggingface
```

脚本里已 `setdefault`，命令行再显式给一遍更稳。

### 教训 5：预热后的真实性能

| 测量时机 | det 单帧 | 说明 |
|---|---|---|
| 首次（含模型加载） | 1.03 s | 会把可行性判断完全带偏 |
| 预热后 | **24 ms** | 真实稳态值，快 38 倍 |

真实全片基准（716s / 60fps / 42918 帧 / 1080p HEVC）：det 累计 **987s（16.5min）**，加 OCR 与解码合计 **1185.7s ≈ 19.8 分钟**。

**任何性能结论都必须预热后再测。**

### 教训 6：ROI 必须逐片确认

本片字幕位于 y **82%~96.6%**（白字黑描边、底部居中），据此把默认 ROI 定为 `--roi-top 0.78 --roi-bot 0.98`（上下各留余量）。换片必须重新看小样——ROI 是比例值，与分辨率无关，但**与字幕在画面中的位置有关**。

## 归并规则细节（`merge_entries`）

相邻两条合并的条件是**同时**满足：

- rapidfuzz `fuzz.ratio(prev_text, cur_text) > --sim`（默认 **80**）；
- 时间间隙 `gap = cur.start - prev.end` 满足 `gap <= --merge-gap`（默认 **0.35s**）**或** `gap <= 0.05s`（几乎无间隙时无条件合并）。

合并时保留更长的那个文本（应对同一句在两帧里识别长度不同）。之后再做两步清理：

- 重叠裁剪：若后一条的 start 早于前一条的 end，把前一条的 end 收到后一条的 start；
- 时长过滤：丢弃时长小于 `--min-dur * 0.5` 的条目（默认 0.15s）。

## 覆盖验证方法

判断「有没有漏句」，不要靠感觉，靠空洞：

1. 列出所有 `next.start - prev.end > 6s` 的空洞；
2. 逐个回到视频对应时间点抽查；
3. 若都是真实的过场（切场景、纯 UI、游戏画面），则无漏句。

实测该片 11 个 >6s 空洞逐一抽查，**全部为真实无字幕段**。

## 文本质量基线（该片实测）

- 疑似乱码：**0** 条；
- 繁体混入：**1** 条（「減去14天」）——PP-OCR 系已知特性，如需强简体可后处理（如 opencc）；
- ≤2 字条目：**12** 条，均为合法口语（「当然」「没错」）。
