# 已知问题与优化方向

**何时读**：结果里混进了 UI／水印文字且**不能**接受；或者你打算改动脚本的过滤逻辑。

**先读这句**：本 skill 当前版本**只做字幕提取，不做 UI 判别**。它对「字幕矩形区内的其它文字」是**无差别识别**的——只要落在 ROI 里、置信度过关，就会被当成字幕。这是**已知边界，不是 bug**。下面记录问题的完整边界、一次失败的修复尝试，以及可选的优化方向。

---

## 1. 问题是什么

det 把 ROI 内**一切文字**当字幕。游戏实况、模拟经营类视频里，字幕带附近常有：

| 类别 | 实例（真实观测） | 为什么难 |
|---|---|---|
| 常驻水印／台标 | `UID: 224115138`、`夜深人静写算法…`（一集重复 17 次） | 位置固定、高频；但**置信度很高**，`--conf` 挡不住 |
| UI 标签 | 左下角门派名「万花谷 七秀坊」 | 会**粘在字幕前缀**上，合成一条乱码字幕 |
| 按钮／滑块文字 | 底部「后X / +1」、捏脸面板滑块标签 | 与字幕**同带**，几何过滤分不开 |

**为什么 `--conf 0.75` 无效**：这些 UI 文字通常是高对比度白字，OCR 置信度常在 0.9 以上，比真字幕还高。

**为什么矩形 ROI 也解决不了**：这些 UI 与字幕**在同一高度带内**，收紧 `--roi-top/--roi-bot` 会把字幕一起裁掉。

> 这是**所有基于矩形 ROI 的硬字幕工具的共性盲区**。业界成熟的 `video-subtitle-extractor` 同样没有解决（其 issue #39/#359/#95 长期有同类投诉）。

---

## 2. 一次失败的修复尝试（v2，务必先读）

v2 曾试图用**五层过滤器**解决，其中两层被判据方向性错误，**实测严重过度过滤**，已废弃：

| 层 | 判据 | 结果 |
|---|---|---|
| F1 矩形 ROI（`--roi-left/--roi-right` x 裁剪） | 收窄左右边界 | ✅ **有效，建议保留复用** |
| F2 静态格掩码 | 某格被文字覆盖的帧比例 ≥90% → 判为常驻 UI | ❌ **方向错了** |
| F3 底部基线带 | 框 bottom 聚类取主簇 ± 容差 | ❌ **被 F2 带偏** |
| F4 OCR 结果空间过滤 | 对 `rec_boxes` 复用 F2/F3 | ❌ 同上 |
| F5 重复文本报告 | 相同文本 ≥N 次记入 suspects | ⚪ 仅报告，无害 |

**F2 为什么错**：它假设「连续对话时字幕格会有空白 → 占据率低」。实测**恰恰相反**——连续对话时字幕格占据率 **≥90%**，于是**真实字幕格被判定为静态 UI 而整片剔除**：852 条字幕只剩 58 条，被保留下来的反而是转瞬即逝的 UI 框。

**F3 为什么连带错**：F2 把真字幕剔干净后，剩下的全是瞬态 UI 框，F3 就在这堆垃圾上聚类出了**错误的底部基线带**（ROI 相对 0.094~0.344），进一步误杀。

**结论（要记住的教训）**：**「占据率／出现频率高」不等于「是 UI」**——字幕本身在连续对话时也是高频的。任何拿"高频"当 UI 判据的方案，都必须同时约束「**位置固定**」这一维，否则必然误杀字幕。

## 3. 调研结论：`video-subtitle-extractor` 值不值得抄

调研了 `YaoFANGUK/video-subtitle-extractor`（VSE，9.5k star，2026-04 最后提交）。**结论：不建议整体采用，只值得借鉴一个算法点。**

它是**外部件胶合应用**，不是算法库：找有字幕的帧外包给**闭源二进制 VideoSubFinder**，识别外包给 PaddleOCR 3.x，自研的只有后处理。

| 环节 | VSE 做法 | 对我们的价值 |
|---|---|---|
| 找有字幕帧 | 闭源 VideoSubFinder | ❌ 不可移植；且**只在 ROI 内找字、不剔 UI** → 换上去不解决本问题 |
| 字幕区检测 | **用户手动画框**（默认 `0.78,0.99,0.05,0.95`）+ 后验坐标统计 | ❌ 与本 skill 的 `0.78/0.98` 几乎一致，无增量 |
| **水印剔除** | **坐标出现频次** `Counter.most_common()` 取前 5 | ✅ **唯一有增量的点** |
| 去重分段 | Levenshtein ratio 0.80 | ⚪ 与本 skill 的 `rapidfuzz > 80` 等价 |

**两个关键事实**：

- README 宣称的"基于深度学习的字幕区域检测"是**营销措辞**——源码里没有神经网络 ROI 检测器，所谓"自动定位"是拿 OCR 结果做 `Counter` 统计 + **人工 y/n 确认**。
- **RTX 5070 Ti (sm_120) 上 VSE 反而更难跑**。README 原文：*"NB 50系需 cuda12.8.0 及以上，但 Paddle3.3.1 目前仍未支持，建议使用 Directml 通用版本"*；2.2.0 只发 CPU 包，CI 最高 CUDA 12.6。而本 skill 的 `transformers + gpu:0` **已实测在 sm_120 可用**。采用 VSE = 从"已验证可用"退回"官方未测试"。

**VSE 唯一可独立借鉴的算法（与其引擎完全解耦，约 40 行，零新依赖）**：

> **同一坐标高频重复出现的文本 = 水印**（按**坐标**判定，不看文本内容）。

原文注释：*"水印区域（台标）的坐标在水平和垂直方向都是固定的……将一直具有固定坐标的文本区域选出"*。

**但要注意**：这个判据**连带约束了"位置固定"**，所以它**不会**像 F2 那样误杀字幕——字幕每句位置虽同带但**框的宽高和内容在变**；而水印的框**逐像素固定**。这正是 F2 缺失的那一维。

## 4. 待验证的优化方向（尚未实施）

若确实需要干净结果，以下方向**按优先级排列，均未实施、未验证**。实施前必须遵守两条铁律：

1. **必须新开一集小样做回归**（如 `--seconds 120 --keep-frames`），对照已知污染清单，验收标准 = **0 污染且字幕保留率 ≥95%**；
2. **每个判据都要有独立开关**，便于单条回退对比——不要一次叠五个（v2 的教训）。

### 方向 A — 坐标频次水印检测（复刻 VSE，最高优先）

- **数据源用阶段 1 的逐帧 det 框**（每帧都有，样本充足），**不要用 OCR 结果**（只覆盖约 3~5% 的帧，样本不足、频次统计不稳）。
- 按量化坐标（如 8px 网格，或 ROI 相对 0.01）做 `Counter` 归并；出现频次 ≥ `max(3, 0.15 × 含字帧数)` 的坐标簇判为水印。
- 只按**坐标几何**判定，不看文本内容——与文本无关，因此不误杀"同一句话反复出现"的正常字幕。

### 方向 B — `ocr_middle()` 保留框坐标

- 现状：函数内部已取到 `rec_boxes`（用于空间过滤），但**过滤后丢弃了坐标**，只返回 `(text, conf)`。
- 改造：保留 `(bbox, text, score)`，使下游能做空间级与内容级过滤。
- 注意：`rapidocr` 分支可能拿不到框坐标，需降级策略（拿不到就跳过空间过滤、宁多不漏）。

### 方向 C — 行高／纵横比离群过滤

- 真实字幕行高稳定（480p 下约 20~30px）；HUD 按钮常高度／纵横比异常。
- 统计框 `h` 与 `aspect=w/h`，取中位数 ± 容忍带（或中位数 + MAD）剔除离群。
- 待定：用 det 框（样本多更稳）还是 OCR 框（更贴近文本）。

### 方向 D — 左下角子区高频前缀剥离

- 针对「万花谷 七秀坊」这类**粘在字幕前缀**的 UI 标签。
- 判据：框位于 ROI 左下角子区（如 `x < 0.35` 且 `y > 0.9`，ROI 相对坐标）**且**同一几何位置全片高频复用 → 判为 UI。
- 同样必须**同时约束位置固定 + 高频**（见 §2 教训），否则会误杀左下角区域的正常字幕。

### 方向 E — `blacklist.json` 可配置黑名单（人工兜底）

- `{"夜深人静写算法": "", "UID: \\d+": ""}`，写 SRT 前 `re.sub`。
- 文件**不存在时静默跳过**；CLI 加 `--blacklist <path>`。
- 定位是**兜底**，不能指望它自动——VSE 自己的 `typoMap.json` 实际也只有 5 条人工映射。

### 不推荐的做法（已证伪，别重蹈）

- ❌ **静态格占据率／出现频率当 UI 判据**（v2 的 F2，方向性错误，见 §2）。
- ❌ **在剔干净字幕后的残框上做聚类**（v2 的 F3，会聚出错误基线）。
- ❌ 一次叠加多层过滤器且不给独立开关——无法定位是哪层在误杀。

---

## 5. 现实建议

- 若 UI 污染**不影响下游使用**（例如只是偶尔一条乱码、且下游是摘要类任务）：**接受现状**，不要改脚本。这是最省事的选项。
- 若必须干净：从**方向 A** 开始，单独实施、单独小样验证，通过后再考虑 B/C/D。
- **不要**为了这一条问题去切换整套工具链（VSE 在 sm_120 上的可行性更差，见 §3）。
